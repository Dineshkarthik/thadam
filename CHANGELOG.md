# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). While the project is pre-alpha (pre-1.0), any release may contain breaking changes; versioned on-disk formats refuse unknown versions rather than guessing.

## [Unreleased]

Thadam is early in its first milestone (M1 / MVP v0.1). No releases exist yet; this section summarizes what the development history has built so far. Detailed status: [docs/design/readiness.md](docs/design/readiness.md) and ARCHITECTURE.md section 21.

### Added

- **Workspace and guardrails**: eleven-member Cargo workspace (ten library crates plus the CLI), MSRV Rust 1.89, pinned toolchain, `cargo deny` policy, dependency-direction guard, nextest, CI on Linux x86_64 and ARM64.
- **Design corpus**: `ARCHITECTURE.md`, the ADR set in `docs/design/adr/` (nine accepted on 2026-10-07, including the delivery guarantees and claims register ADR-0011), owner-decision and readiness registers, and five spike reports (S1 WAL, S2 MQTT, D8 record representation, config YAML, filter language).
- **`thadam-core`**: canonical event model (times with time domains, quality status/flags, hierarchical identity, extended values, shape-shared positional records), error model with stable codes, connector traits (`Source`, `BatchSink`, `SegmentSink`), disk budget, conformance-test utilities in `thadam-testkit`.
- **`thadam-config`**: config `version: 1` — YAML loading with a strict dialect (strict booleans; no anchors/aliases/merge keys/tags; parse budget; duplicate-key errors), `${env:}`/`${file:}` secret interpolation with redaction, multi-error diagnostics with paths and line numbers, connector-kind validation through the registry, config hash (algorithm v1), memory estimate, JSON Schema export, Parquet field-ID and identity-level-ID assignment, per-sink WAL consumer policies (`required`, `max_lag`, `start_from`).
- **`thadam-wal`**: custom segmented log — one-writer group commit, `always`/`interval`/`never` fsync policies, durable cursors, retention and `on_full` (`block`/`drop_oldest`), crash recovery with torn-tail truncation, gaps surfaced to readers. **On-disk format v1 is versioned but not frozen** (ADR-0004 pending a reference-hardware re-run).
- **`thadam-transform`**: synchronous pure chains — router, JSON decode, event IDs (WAL-derived or content-derived `event_id.key`), message-level dedup with warm start, `explode` with parent paths, UCUM unit conversion (element-wise on arrays), time extraction with domains and skew flagging; steps `validate`, `on_change`, `filter`, `sample`, `enrich`, `rename`, `project`, `cast` (all config-reachable).
- **`thadam-runtime`**: source/chain/sink drivers, supervisor with component states, ordered shutdown and startup recovery, `thadam.json`/`wal.json` identity split, quarantine routing, primary-chain metric attribution.
- **`thadam-mqtt`**: MQTT 3.1.1 source — persistent sessions, acknowledge-after-commit with ordered acks, epoch-scoped ack handles, session-loss detection with resubscribe, byte-accounted queue with disconnecting guard, QoS 0 counted drops, in-process TLS/mTLS relay with rustls+`ring` (client library built without TLS features).
- **`thadam-http`**: HTTP source — `listen` mode (`POST` per message, `204` only after commit, `503` with `Retry-After` under backpressure, `413`, bearer-token auth, optional rustls+`ring` TLS, loopback bind by default) and `poll` mode (periodic GET/POST with jittered backoff and per-request timeouts; at-most-once, documented).
- **`thadam-grpc`**: gRPC source (`kind: grpc`) serving a tonic `thadam.ingest.v1.Ingest` service — unary `Publish` answers only after commit, `PublishStream` acks in order and counts committed messages, `RESOURCE_EXHAUSTED` under backpressure, `INVALID_ARGUMENT` above `max_message_bytes`, bearer-token auth, optional rustls+`ring` TLS, loopback bind by default.
- **`thadam-arrow`**: event-to-Arrow encoding with envelope/lineage columns and stable Parquet field IDs (ADR-0013 decisions: unsigned default `Native`, list element name, 16-byte schema fingerprint).
- **CLI (`thadam`)**: `validate` (with `--allow-unresolved`), `schema`, `version`, `run` (graceful signal handling, admin override flags, `--repair`), `status` against the admin API.
- **Admin API and observability**: `/healthz`, `/readyz`, `/metrics` (OpenMetrics), `/status` (components, cursors, WAL, budgets); Prometheus metrics; structured lossy logging.
- **Documentation**: README with branding and status banner, this changelog, contributing and security policies, issue/PR templates, and the mdBook user documentation under `docs/`.
- **`thadam-segments`**: the Parquet segment sink with rotation, the commit-then-ship finalize sequence (D18), the segment catalog (append-only, CRC-checked, footer rebuild on recovery), coverage markers for empty datasets, quarantine sink, and the shared-disk-budget eviction order.
- **`thadam-object-store`**: the object-store shipper as a `kind: object_store` service — oldest-first uploads from the segment catalog with bounded concurrency, deterministic keys (ADR-0013), create-if-absent with HEAD size + `thadam-sha256` verification on conflict (Fatal `sink.object_key_collision` on mismatch), multipart above a threshold, startup capability probe (conditional put, clock skew, metadata), unbounded jittered retry, local retention modes, failpoints `ship::after_put_before_mark` and `ship::mid_multipart`, and Docker tests against SeaweedFS's S3 API (`docker_s3`; public Docker Hub image pinned by tag — MinIO stopped publishing community images in late 2025).

- **Connector metrics channel and ship/segment metrics** (`thadam-core`, `thadam-runtime`, `thadam-segments`, `thadam-object-store`): a typed metrics hook in `thadam-core` (`ConnectorMetric` plus the `MetricsRecorder` on `SinkContext`/`ServiceContext`) lets connectors report through the runtime's `MetricsSink` — wired at every context construction, replay included. The Prometheus exporter gains `thadam_ship_bytes_total`, `thadam_ship_uploads_total{outcome}` (`ok`/`conflict_equal`/`retry`/`fatal`), `thadam_ship_retry_age_seconds`, and `thadam_ship_upload_seconds` from the shipper, and `thadam_segment_files{state}`, `thadam_segment_bytes{state}`, and `thadam_segment_finalize_seconds` from the Parquet sink and the shipper, which republish absolute per-state catalog totals on every transition. - **`thadam-mqtt` attributes**: messages now carry the normalized `topic` attribute alongside the documented `mqtt.topic`. The chain's `match.topic` filter and `{topic.N}` identity templates read `topic` (`docs/src/configuration/datasets.md`); without it, every broker message was consumed with zero matched datasets and zero written rows (PR15 end-to-end discovery).
- **`thadam replay` and `thadam inspect`** (PR17): `thadam replay <pipeline.yaml> --from <position|-45m|RFC3339> [--to ...] --sink <id> [--output <dir>]` re-runs a sink's chain over the retained WAL range into a separate directory (never the production sink directory or cursor), printing the replay id and output path. `thadam inspect wal|cursors|segments --sink|sample` are read-only views of a data directory, human-readable by default and `--json` for machine output, and work while `thadam run` holds the data directory. Supporting API: `thadam-wal` gains a read-only `inspect(dir)` that never takes the writer lock, `thadam-segments` gains a read-only `catalog::inspect(root)`, and `thadam-runtime` gains `ReplayOutput::SeparateDirAt` for a caller-chosen output path, refused inside `sinks/` and `wal/`.
- **`thadam-mcap`**: the MCAP / rosbag2-MCAP file source (`kind: mcap`, ADR-0007 stage 2) — replays one or more MCAP files as a finite stream merged in log-time order, with directory expansion, topic allow-lists (exact or `/`-suffix prefix), inclusive `start`/`end` log-time bounds (RFC 3339 or integer nanoseconds), and replay pacing (`max`, `realtime`, or a numeric factor; gaps beyond a day clamp). Payloads stay raw; `decode: ros2` pre-flights `ros2msg` schemas through the `thadam-ros2-msg` compiler at open and attaches the compiled shape's field names as `mcap.ros2.fields`, while decoding into records stays with the transform chain via the new `thadam_mcap::decode_ros2(schema_name, schema_text, payload)` helper (unit-tested against `sensor_msgs/JointState`). Every message carries `mcap.*` attributes (topic, schema name/encoding, message encoding, channel id, sequence, log and publish times) plus the normalized `topic` attribute; with `pace: max` the ingest time is the MCAP log time so replays are byte-deterministic (paced replays stamp the wall clock). Acknowledgements are no-ops (`ack_mode: none`): files re-read idempotently from the start. Streaming reads are safe Rust (no mmap; one chunk at a time), truncated or corrupt files fail with classified errors rather than panics, and dropped `next_batch` futures lose nothing because paced batches are staged source-side. Conformance-relevant clauses verified in-crate (the broker-dependent clauses of the testkit suite do not apply to a static file source).
- **`thadam export` and the MCAP exporter** (ADR-0015, draft): `thadam export <pipeline.yaml> --mcap <OUT> --from <POINT> [--to <POINT>] [--source <ID>]... [--encoding <SOURCE>=json|raw]... [--schemas <FILE.mcap>]... [--force]` writes a retained WAL range to one indexed MCAP file, with `--from`/`--to` in the `thadam replay` forms (position, `-45m`, RFC 3339). It reads the WAL only and never commits a cursor, takes the data-directory lock (refused while `thadam run` holds it), and writes `<OUT>.tmp`, which is synced and renamed into place. The library side, `thadam_mcap::McapExporter` (commit edcdcc1), writes one channel per `(source, topic)` that keeps its message encoding and resolves schema text through a `SchemaResolver`, because the WAL carries schema names but not schema text; the CLI reads that text from the configuration's `mcap` source files and from `--schemas`. WAL gaps become `thadam.gap` records, unresolved schemas are listed in `thadam.unresolved_schemas`, and `thadam.provenance` records the thadam version, WAL epoch, first and last exported position, and node id. A topic whose messages disagree on encoding or schema is an error. Messages from other sources default to `json` when every dataset reading the source decodes JSON, and to `application/octet-stream` otherwise. Docs: [`thadam export`](cli/export.md).
- **`thadam-modbus`**: Modbus TCP polling source (`kind: modbus`) over `tokio-modbus` 0.17. Each poll reads every configured `holding`, `input`, `coil`, or `discrete` range and emits one JSON message (`{ "<name>": value-or-array, ..., "ts_us": poll time }`) with `modbus.address`, `modbus.unit_id`, and `topic = modbus/<unit_id>` attributes. Values decode as `u16`, `i16`, `u32`, `i32`, `f32` (with `big` or `little` word order), `bool`, or `raw`, with optional `scale` and `offset`. Delivery is at-most-once per poll (`ack_mode: none`). Connection failures and timeouts drop the session and retry with jittered backoff; a read the device refuses with a Modbus exception becomes `null`, is named in `modbus.exceptions`, and leaves the session up.
- **`thadam-nats`**: the NATS JetStream batch sink (`kind: nats`) over `async-nats` 0.50 (rustls + `ring` only). One acknowledged message per event bounded by `max_in_flight`, JSON envelope (`_event_id`, `_ingest_time`, `_event_time`, `_quality_status`, the identity levels, then the record fields — later regions never shadow lineage), subject templating at whole-token granularity (`thadam.{dataset}.{robot}`), and a `Nats-Msg-Id` header set to the event id so a stream's duplicate window deduplicates the runtime's retries server-side. `open` probes the stream and reports `idempotent_batch` only when `duplicate_window > 0`, `at_least_once` otherwise; a missing stream is a configuration error unless `create_stream: true` (default `false`, operators own provisioning). Credentials: token, user+password, or a NATS credentials file (secrets pre-resolved by `${env:}`/`${file:}` and never logged); TLS with CA and optional client cert via rustls+`ring`. Errors classify as transient (timeouts, no responders, connection lost), fatal (rejected credentials, permission violations — a denied publish is never acknowledged, so the sink records the server's `Permissions Violation` announcement and reports the following ack timeout as fatal), or per-event permanent (payload over the server's `max_payload` or the stream's `max_msg_size` → quarantine). One dataset per sink entry until the batch contract groups per dataset (ADR-0002). Docker-gated tests against `nats:2.12.2 -js` (public image, pinned tag, `THADAM_TEST_NATS_IMAGE` to re-pin): publish/consume-back, broker stop/start recovery exactly-once, `Nats-Msg-Id` dedupe, missing-stream config error, delivery-class probe, `create_stream`, per-event rejection (unrenderable subject, `max_payload`, `max_msg_size`), no responders, token and user/password auth with wrong-credential and denied-publish cases, mutual TLS.
- **`thadam-can`**: SocketCAN source (`kind: can`, Linux only) over `socketcan` 4 (`tokio` feature) and `can-dbc` 10. Receives classic and CAN FD frames from one interface with kernel receive filters (`{id, mask, extended}`). `emit: raw` (default) sends the frame bytes with `can.id` (hex), `can.extended`, `can.fd`, `can.dlc`, `can.interface` and `topic = can/<interface>/<id hex>`. `emit: decoded` decodes DBC signals (Intel and Motorola bit order, signedness, scale and offset, IEEE float signals, simple multiplexing) into JSON `{ "<signal>": value, ..., "ts_us": <timestamp> }` with `topic = can/<interface>/<message name>`; ids missing from the DBC are emitted raw or dropped (`unknown: raw | drop`). CAN has no flow control, so delivery is at-most-once (`ack_mode: none`): the receive task never waits on the pipeline, frames that do not fit its 4096-message queue are dropped and counted, and the running total rides on later messages as `can.dropped`. A receive failure is surfaced as a transient error after queued messages are delivered, and the source reopens after `close`. The crate compiles on every OS: the transport is behind `cfg(target_os = "linux")`, decoding runs behind an internal `FrameSource` trait with in-memory tests, and building the source elsewhere returns a clear configuration error. `vcan` end-to-end tests are `#[ignore]`d (they need a kernel with CAN support).
- **`thadam-clickhouse`**: the ClickHouse batch sink (`kind: clickhouse`, ADR-0008) over the official `clickhouse` 0.15 client (rustls + `ring` only, `cargo tree -i aws-lc-sys` stays empty), registered in `thadam-cli` behind the default-on `clickhouse` feature. Events encode through `thadam-arrow` into one dynamically built Native block per batch (`insert_native()`; the only vendor-maintained path for runtime-typed columns, since `clickhouse-ext-arrow` pins arrow 58 against the workspace's 60). `open` probes the server version, runs `DESCRIBE TABLE` and validates the dataset schema against it (every mismatch listed in one `Config` error; the sink never runs `CREATE` or `ALTER`), then probes the engine and the `replicated_`/`non_replicated_deduplication_window` settings (table, falling back to server default) and reports `idempotent_batch` or `at_least_once` accordingly. With deduplication on, each insert carries `insert_deduplication_token = {epoch}-{sink}-{first}-{last}` (a function of the batch id, so retries and post-crash replays repeat it); inserts always run with `async_insert = 0`. Config: `url`, `database`, `table`, `user`, `password` (via `${file:}`), `compression`, `request_timeout`, `dedup: auto|token|off`, `columns` mapping, `datasets` (exactly one per sink entry until the batch contract groups per dataset). Errors: parse, type, range, and constraint failures are permanent (the runtime bisects; error context keeps the exception code, never the row the server quotes), memory, too-many-parts, too-many-queries, and timeouts are transient (retried with the same token), authentication and permission failures are fatal; the code tables were checked against ClickHouse v26.8.22.13's `ErrorCodes.cpp`. Conversions that ClickHouse would turn into silent NULLs (narrowing, `FixedString` length, `DateTime`/`DateTime64` range) are checked in the sink and fail the batch instead. Known limits: Native insert bodies are sent uncompressed by the vendor crate in 0.15.2 (`compression` only affects probe responses), `Tuple`/`Map`/`Enum`/`Decimal`/nested arrays/records are not supported, a table with no deduplication window duplicates a batch retried after an unknown outcome (reported as `at_least_once`). Docker-gated tests against `clickhouse/clickhouse-server:26.8.22.13` (public LTS image, `THADAM_TEST_CLICKHOUSE_IMAGE` to re-pin): read-back of every column family, same-token retry with and without a window, stop/start recovery, a frozen server, poison rows and bisection, schema mismatch with nothing created or altered, bad credentials, and the batch-sink conformance suite.
- **`thadam-mqtt` publish sink**: the MQTT batch sink (`kind: mqtt_publish`), one JSON message per event with the same envelope as the NATS sink (`_event_id`, `_ingest_time`, `_event_time`, `_quality_status`, identity levels, then record fields). Topics come from a template (`thadam/{dataset}/{robot}`) and are checked for wildcards, NUL, empty levels, and `$`-prefixed roots at validation and per event. `qos: 1` (default) reports `at_least_once` and completes a publish only on its PUBACK; `qos: 0` reports `at_most_once`. `max_in_flight` bounds unacknowledged publishes, `request_timeout` bounds each PUBACK wait, and `max_message_bytes` rejects oversized events individually. Connection loss is transient and the batch is retried whole. A packet-id collision that survives a reconnect makes the sink rebuild its client and session before the next publish. `mqtts://` with `tls` (CA, optional client cert and key) through rustls + `ring`. Docker-gated tests against `eclipse-mosquitto:2` and `emqx/emqx:5.8.6` (public images, pinned tags): QoS 1 and QoS 0 delivery to a test subscriber, broker restart mid-batch with transient failure and at-least-once retry, TLS and mutual TLS, and the batch-sink conformance suite.
- **`pose` and `joint_state` transform steps** (robotics validation; see `docs/src/concepts/robotics-conventions.md`): two new chain steps flag ROS-shaped records — quality is data, nothing is dropped. `pose` reads `<prefix>.position.{x,y,z}` and `<prefix>.orientation.{x,y,z,w}` (`f32`/`f64`; `prefix` defaults to `pose`, the flattened `geometry_msgs/PoseStamped` layout): a null or non-numeric component is `INVALID`/`pose_missing_field`, a NaN or infinite one is `INVALID`/`pose_not_finite`, a quaternion norm farther than `quaternion_tolerance` (default `0.001`, 0 < t < 1) from 1 is `OUT_OF_RANGE`/`quaternion_not_unit`, and a missing or empty frame id (default `header.frame_id`; an explicit `frame_field: null` skips the check) is `INVALID`/`missing_frame_id`. `joint_state` follows `sensor_msgs/JointState` semantics over configurable fields (defaults `name`/`position`/`velocity`/`effort`; typed `f32`/`f64` arrays and generic float lists): every array must be empty or as long as the name list (`joint_state_length_mismatch`), names must not repeat (`duplicate_joint_name`), and values must be finite (`joint_state_not_finite`) — all `INVALID`. Supporting pieces: `QualityFlags` gains `INVALID` (bit 8, product.md section 22's `invalid`; dashboards can now filter structurally-bad rows), `thadam validate` accepts both kinds (the `joint_state` array fields are checked against the dataset's declared fields, while the `pose` step's decoder-produced dotted fields, like an `enrich` table, resolve when the chain compiles at startup), and the two steps are documented in `docs/src/configuration/transforms.md` with a new concepts page.

### Fixed

- **`thadam-cli` crypto provider**: the composition root now installs the ring rustls crypto provider at process start. `object_store`/`reqwest` are built `rustls-no-provider` (ADR-0020), so every `thadam run` of a config with an `object_store` sink previously panicked with "No rustls crypto provider is configured" when the shipper built its S3 client (PR15 end-to-end discovery); the MQTT TLS relay builds on the same provider.
- **`thadam-object-store` probe**: the startup capability probe checked user-metadata round-trip *after* the conditional-create conflict put. On stores that ignore `If-None-Match` (observed on SeaweedFS 3.81) that second create overwrites the probe object and its attributes, so the probe reported `returns_metadata = false` for stores that do return metadata, silently degrading conflict verification to size-only. The metadata check now runs before the conflict put.
- **`thadam-config`**: the config now accepts all eight transform kinds the engine implements — `sample`, `enrich`, `rename`, `project`, and `cast` are added to `validate`, `on_change`, and `filter`, using the engine's option names.
- **`thadam-config`**: the config gains the engine's `null:` predicate test, the `on_change` `{ field, deadband }` entry form, and `unit: rfc3339` with `default_offset` for dataset `time`.
- **`thadam-config`**: `dedup` without `event_id.key` is now a validation error (`config.invalid`); it was a warning. This matches ADR-0011 D17.
- **`thadam run`**: the logging guard now stays alive for the whole run; application log lines after startup are no longer silently dropped.
- **Log-format spellings** are unified on `json`/`pretty`: config `observability.logs.format` takes those values with `text` accepted as a deprecated alias for `pretty` (validation warns), and `thadam run` without `--log-format` uses the config value (default `json`) instead of the previously hardcoded `pretty`.
- **`thadam-runtime` quarantine no longer holds its sink's cursor**: a reject used to cap the owning segment sink's WAL cursor (`Quarantine::floor`) until the quarantine Parquet segment rotated and became durable (`quarantine.rotation.max_age`, 5 minutes by default), pausing the sink's cursor, its uploads, and shipping behind one pending reject. Rejects are now appended and fsynced to a small per-quarantine staging file (`quarantine/<sink>/rejects.staging`: append-only frames of `len | crc32c | payload`, one per push) and the cursor may pass them as soon as that fsync returns; the quarantine segment is built from the same rows on its own rotation cadence and staging is truncated (or rewritten without its dead prefix) once the covering segment is durable. After a crash, staged rejects not yet in a durable quarantine segment are replayed into the next one exactly once, filtered by the quarantine's durable WAL position, with torn staging tails cut like the WAL's. Staging bytes are charged to the quarantine disk budget, the open quarantine segment is closed early when about 8 MiB is staged or the budget is full, and a failed quarantine append is healed by replaying staging. Quarantine segment ranges now chain contiguously across pushes: before, two rejects separated by a quarantine rotation left a hole that stalled the quarantine watermark. No configuration change. New failpoint `quarantine::after_stage`.
- **`thadam-runtime` / `thadam-segments` sink-level rejects survive a crash after the sink's segment is durable**: a reject the sink itself returns from `append` (for example a value its columns cannot hold) is only known after `append`, but the Parquet sink could finalize the segment holding that batch inside the same `append` (rotation by rows or bytes, or eviction at `max_open_files`). A crash before the reject was staged left a sink position the restart treated as complete, the re-read skipped the sink append, and the reject was never regenerated. `SegmentSink` gains a defaulted `defer_durability(bool)`; the segment driver sets it, and the Parquet sink then runs a rotation or eviction that the current batch triggers at the start of the next `append`, `poll_commit`, or `finalize_all`, always after the driver staged the batch's rejects. New failpoint `segment::after_append_before_stage`.
