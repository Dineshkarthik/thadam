# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). While the project is pre-alpha (pre-1.0), any release may contain breaking changes; versioned on-disk formats refuse unknown versions rather than guessing.

## [Unreleased]

Thadam is early in its first milestone (M1 / MVP v0.1). No releases exist yet; this section summarizes what the development history has built so far. Detailed status: [docs/design/readiness.md](docs/design/readiness.md) and ARCHITECTURE.md section 21.

### Changed

- **One website folder**: the homepage and the user documentation now live under `website/` (`website/public/` at `/`, `website/docs/` at `/docs/`). `website/scripts/build.sh` builds one artifact in `website/dist/`, and `check.py` verifies it. The mdBook sources moved from `docs/` with history kept; `docs/` now holds the design records only. Brand assets are consolidated in `thadam-assets/brand/`, replacing `thadam-brand-kit/`. CI builds the site and uploads `website/dist` as an artifact; deployment is not configured here.
- **Site polish**: the homepage gains a "How it works" diagram, a working "Get started" link, social cards (`og:image`, Twitter card, JSON-LD), and a web app manifest. Docs pages get per-page social metadata, and the docs header links back to the homepage. The mdBook print page is disabled to reduce size. `check.py` enforces a homepage size budget and the new metadata.
- **Light and dark themes**: the homepage, the 404 page, and the docs share one theme toggle and one saved choice (`mdbook-theme` in local storage). The choice is applied before first paint, and without a choice the site follows the system setting. The docs use graphite for dark mode and warm white for light mode, with brand tokens throughout.
- **Homepage data-flow diagram**: rebuilt as an HTML grid that lists every source and sink with its status pill (the old SVG showed four generic boxes and clipped long labels). Sources and sinks now match the status table, and the layout stacks on narrow screens.
- **Site polish pass**: the stylesheet is consolidated into one dark-mode path and one reduced-motion block. Status labels are pills (Available, In progress, Planned) so colour is never the only signal. The homepage and docs introduction are rewritten to the claims register: "Nothing that Thadam acknowledged is lost" is replaced with "acknowledged data survives a process crash when fsync is enabled". `check.py` lints for forbidden claim wording and checks status labels and the single `h1`.
- **Homepage hero art**: the hero illustration is now the light and dark artwork, cropped to the illustration (`thadam-illusion-light-hero.png` and `thadam-illusion-dark-hero.png`) instead of the CSS grid plane.
- **Agent instructions**: `AGENTS.md` is the source of truth for agents; `CLAUDE.md`, `.cursor/rules/website.mdc`, and `.github/copilot-instructions.md` point to it.

- **`thadam-mqtt` attributes**: messages now carry the normalized `topic` attribute alongside the documented `mqtt.topic`. The chain's `match.topic` filter and `{topic.N}` identity templates read `topic` (`docs/src/configuration/datasets.md`); without it, every broker message was consumed with zero matched datasets and zero written rows (PR15 end-to-end discovery).
- **`thadam replay` and `thadam inspect`** (PR17): `thadam replay <pipeline.yaml> --from <position|-45m|RFC3339> [--to ...] --sink <id> [--output <dir>]` re-runs a sink's chain over the retained WAL range into a separate directory (never the production sink directory or cursor), printing the replay id and output path. `thadam inspect wal|cursors|segments --sink|sample` are read-only views of a data directory, human-readable by default and `--json` for machine output, and work while `thadam run` holds the data directory. Supporting API: `thadam-wal` gains a read-only `inspect(dir)` that never takes the writer lock, `thadam-segments` gains a read-only `catalog::inspect(root)`, and `thadam-runtime` gains `ReplayOutput::SeparateDirAt` for a caller-chosen output path, refused inside `sinks/` and `wal/`.
- **`thadam-mcap`**: the MCAP / rosbag2-MCAP file source (`kind: mcap`, ADR-0007 stage 2) — replays one or more MCAP files as a finite stream merged in log-time order, with directory expansion, topic allow-lists (exact or `/`-suffix prefix), inclusive `start`/`end` log-time bounds (RFC 3339 or integer nanoseconds), and replay pacing (`max`, `realtime`, or a numeric factor; gaps beyond a day clamp). Payloads stay raw; `decode: ros2` pre-flights `ros2msg` schemas through the `thadam-ros2-msg` compiler at open and attaches the compiled shape's field names as `mcap.ros2.fields`, while decoding into records stays with the transform chain via the new `thadam_mcap::decode_ros2(schema_name, schema_text, payload)` helper (unit-tested against `sensor_msgs/JointState`). Every message carries `mcap.*` attributes (topic, schema name/encoding, message encoding, channel id, sequence, log and publish times) plus the normalized `topic` attribute; with `pace: max` the ingest time is the MCAP log time so replays are byte-deterministic (paced replays stamp the wall clock). Acknowledgements are no-ops (`ack_mode: none`): files re-read idempotently from the start. Streaming reads are safe Rust (no mmap; one chunk at a time), truncated or corrupt files fail with classified errors rather than panics, and dropped `next_batch` futures lose nothing because paced batches are staged source-side. Conformance-relevant clauses verified in-crate (the broker-dependent clauses of the testkit suite do not apply to a static file source).
- **`thadam export` and the MCAP exporter** (ADR-0015, draft): `thadam export <pipeline.yaml> --mcap <OUT> --from <POINT> [--to <POINT>] [--source <ID>]... [--encoding <SOURCE>=json|raw]... [--schemas <FILE.mcap>]... [--force]` writes a retained WAL range to one indexed MCAP file, with `--from`/`--to` in the `thadam replay` forms (position, `-45m`, RFC 3339). It reads the WAL only and never commits a cursor, takes the data-directory lock (refused while `thadam run` holds it), and writes `<OUT>.tmp`, which is synced and renamed into place. The library side, `thadam_mcap::McapExporter` (commit edcdcc1), writes one channel per `(source, topic)` that keeps its message encoding and resolves schema text through a `SchemaResolver`, because the WAL carries schema names but not schema text; the CLI reads that text from the configuration's `mcap` source files and from `--schemas`. WAL gaps become `thadam.gap` records, unresolved schemas are listed in `thadam.unresolved_schemas`, and `thadam.provenance` records the thadam version, WAL epoch, first and last exported position, and node id. A topic whose messages disagree on encoding or schema is an error. Messages from other sources default to `json` when every dataset reading the source decodes JSON, and to `application/octet-stream` otherwise. Docs: [`thadam export`](cli/export.md).
- **`thadam-modbus`**: Modbus TCP polling source (`kind: modbus`) over `tokio-modbus` 0.17. Each poll reads every configured `holding`, `input`, `coil`, or `discrete` range and emits one JSON message (`{ "<name>": value-or-array, ..., "ts_us": poll time }`) with `modbus.address`, `modbus.unit_id`, and `topic = modbus/<unit_id>` attributes. Values decode as `u16`, `i16`, `u32`, `i32`, `f32` (with `big` or `little` word order), `bool`, or `raw`, with optional `scale` and `offset`. Delivery is at-most-once per poll (`ack_mode: none`). Connection failures and timeouts drop the session and retry with jittered backoff; a read the device refuses with a Modbus exception becomes `null`, is named in `modbus.exceptions`, and leaves the session up.
- **`thadam-nats`**: the NATS JetStream batch sink (`kind: nats`) over `async-nats` 0.50 (rustls + `ring` only). One acknowledged message per event bounded by `max_in_flight`, JSON envelope (`_event_id`, `_ingest_time`, `_event_time`, `_quality_status`, the identity levels, then the record fields — later regions never shadow lineage), subject templating at whole-token granularity (`thadam.{dataset}.{robot}`), and a `Nats-Msg-Id` header set to the event id so a stream's duplicate window deduplicates the runtime's retries server-side. `open` probes the stream and reports `idempotent_batch` only when `duplicate_window > 0`, `at_least_once` otherwise; a missing stream is a configuration error unless `create_stream: true` (default `false`, operators own provisioning). Credentials: token, user+password, or a NATS credentials file (secrets pre-resolved by `${env:}`/`${file:}` and never logged); TLS with CA and optional client cert via rustls+`ring`. Errors classify as transient (timeouts, no responders, connection lost), fatal (rejected credentials, permission violations — a denied publish is never acknowledged, so the sink records the server's `Permissions Violation` announcement and reports the following ack timeout as fatal), or per-event permanent (payload over the server's `max_payload` or the stream's `max_msg_size` → quarantine). One dataset per sink entry until the batch contract groups per dataset (ADR-0002). Docker-gated tests against `nats:2.12.2 -js` (public image, pinned tag, `THADAM_TEST_NATS_IMAGE` to re-pin): publish/consume-back, broker stop/start recovery exactly-once, `Nats-Msg-Id` dedupe, missing-stream config error, delivery-class probe, `create_stream`, per-event rejection (unrenderable subject, `max_payload`, `max_msg_size`), no responders, token and user/password auth with wrong-credential and denied-publish cases, mutual TLS.
- **`thadam-kafka`**: the Apache Kafka batch sink (`kind: kafka`) over `rskafka` `=0.6.0`, pure Rust (rustls + `ring`, gzip and snappy only; no OpenSSL, librdkafka, or aws-lc-sys). One record per event with `acks=all`, the JSON envelope shared with the NATS sink, the event id as the record key and in an `x-thadam-event-id` header, partitioned like the Java client's default partitioner. Delivery class `at_least_once` (the client has no idempotent producer). Topics must already exist: the sink never creates them, and a missing topic is a fatal config error (the client's own named lookups can still trigger broker auto-creation after a topic is deleted mid-run; documented as a limit). Oversized events and refused topic names are per-event rejections (quarantine); missing topics, authorization, and SASL failures are fatal; timeouts and broker unavailability are transient, and a broker that accepts connections but never answers is bounded by `request_timeout`. Credentials: SASL PLAIN (requires `tls`), SCRAM-SHA-256/512; TLS with a CA file and optional client certificate; secrets via `${file:}`/`${env:}`, never logged. Registered in `thadam-cli`. Docker-gated tests against `apache/kafka` 4.3.1 (public image, pinned tag, `THADAM_TEST_KAFKA_IMAGE` to re-pin): publish-and-consume-back, gzip and snappy read-back, broker stop/start between batches, a stalled produce with the broker frozen, oversized events by broker and client limits, missing topic fatal with auto-create off and never created with it on, and the `thadam-testkit` batch-sink conformance suite. TLS, mutual TLS, and SASL PLAIN/SCRAM over TLS are tested against a broker (see the Fixed entry below). Docs: [Apache Kafka](docs/src/sinks/kafka.md).
- **`thadam-can`**: SocketCAN source (`kind: can`, Linux only) over `socketcan` 4 (`tokio` feature) and `can-dbc` 10. Receives classic and CAN FD frames from one interface with kernel receive filters (`{id, mask, extended}`). `emit: raw` (default) sends the frame bytes with `can.id` (hex), `can.extended`, `can.fd`, `can.dlc`, `can.interface` and `topic = can/<interface>/<id hex>`. `emit: decoded` decodes DBC signals (Intel and Motorola bit order, signedness, scale and offset, IEEE float signals, simple multiplexing) into JSON `{ "<signal>": value, ..., "ts_us": <timestamp> }` with `topic = can/<interface>/<message name>`; ids missing from the DBC are emitted raw or dropped (`unknown: raw | drop`). CAN has no flow control, so delivery is at-most-once (`ack_mode: none`): the receive task never waits on the pipeline, frames that do not fit its 4096-message queue are dropped and counted, and the running total rides on later messages as `can.dropped`. A receive failure is surfaced as a transient error after queued messages are delivered, and the source reopens after `close`. The crate compiles on every OS: the transport is behind `cfg(target_os = "linux")`, decoding runs behind an internal `FrameSource` trait with in-memory tests, and building the source elsewhere returns a clear configuration error. `vcan` end-to-end tests are `#[ignore]`d (they need a kernel with CAN support).
- **`thadam-clickhouse`**: the ClickHouse batch sink (`kind: clickhouse`, ADR-0008) over the official `clickhouse` 0.15 client (rustls + `ring` only, `cargo tree -i aws-lc-sys` stays empty), registered in `thadam-cli` behind the default-on `clickhouse` feature. Events encode through `thadam-arrow` into one dynamically built Native block per batch (`insert_native()`; the only vendor-maintained path for runtime-typed columns, since `clickhouse-ext-arrow` pins arrow 58 against the workspace's 60). `open` probes the server version, runs `DESCRIBE TABLE` and validates the dataset schema against it (every mismatch listed in one `Config` error; the sink never runs `CREATE` or `ALTER`), then probes the engine and the `replicated_`/`non_replicated_deduplication_window` settings (table, falling back to server default) and reports `idempotent_batch` or `at_least_once` accordingly. With deduplication on, each insert carries `insert_deduplication_token = {epoch}-{sink}-{first}-{last}` (a function of the batch id, so retries and post-crash replays repeat it); inserts always run with `async_insert = 0`. Config: `url`, `database`, `table`, `user`, `password` (via `${file:}`), `compression`, `request_timeout`, `dedup: auto|token|off`, `columns` mapping, `datasets` (exactly one per sink entry until the batch contract groups per dataset). Errors: parse, type, range, and constraint failures are permanent (the runtime bisects; error context keeps the exception code, never the row the server quotes), memory, too-many-parts, too-many-queries, and timeouts are transient (retried with the same token), authentication and permission failures are fatal; the code tables were checked against ClickHouse v26.8.22.13's `ErrorCodes.cpp`. Conversions that ClickHouse would turn into silent NULLs (narrowing, `FixedString` length, `DateTime`/`DateTime64` range) are checked in the sink and fail the batch instead. Known limits: Native insert bodies are sent uncompressed by the vendor crate in 0.15.2 (`compression` only affects probe responses), `Tuple`/`Map`/`Enum`/`Decimal`/nested arrays/records are not supported, a table with no deduplication window duplicates a batch retried after an unknown outcome (reported as `at_least_once`). Docker-gated tests against `clickhouse/clickhouse-server:26.8.22.13` (public LTS image, `THADAM_TEST_CLICKHOUSE_IMAGE` to re-pin): read-back of every column family, same-token retry with and without a window, stop/start recovery, a frozen server, poison rows and bisection, schema mismatch with nothing created or altered, bad credentials, and the batch-sink conformance suite.
- **`thadam-mqtt` publish sink**: the MQTT batch sink (`kind: mqtt_publish`), one JSON message per event with the same envelope as the NATS sink (`_event_id`, `_ingest_time`, `_event_time`, `_quality_status`, identity levels, then record fields). Topics come from a template (`thadam/{dataset}/{robot}`) and are checked for wildcards, NUL, empty levels, and `$`-prefixed roots at validation and per event. `qos: 1` (default) reports `at_least_once` and completes a publish only on its PUBACK; `qos: 0` reports `at_most_once`. `max_in_flight` bounds unacknowledged publishes, `request_timeout` bounds each PUBACK wait, and `max_message_bytes` rejects oversized events individually. Connection loss is transient and the batch is retried whole. A packet-id collision that survives a reconnect makes the sink rebuild its client and session before the next publish. `mqtts://` with `tls` (CA, optional client cert and key) through rustls + `ring`. Docker-gated tests against `eclipse-mosquitto:2` and `emqx/emqx:5.8.6` (public images, pinned tags): QoS 1 and QoS 0 delivery to a test subscriber, broker restart mid-batch with transient failure and at-least-once retry, TLS and mutual TLS, and the batch-sink conformance suite.
- **`pose` and `joint_state` transform steps** (robotics validation; see `docs/src/concepts/robotics-conventions.md`): two new chain steps flag ROS-shaped records — quality is data, nothing is dropped. `pose` reads `<prefix>.position.{x,y,z}` and `<prefix>.orientation.{x,y,z,w}` (`f32`/`f64`; `prefix` defaults to `pose`, the flattened `geometry_msgs/PoseStamped` layout): a null or non-numeric component is `INVALID`/`pose_missing_field`, a NaN or infinite one is `INVALID`/`pose_not_finite`, a quaternion norm farther than `quaternion_tolerance` (default `0.001`, 0 < t < 1) from 1 is `OUT_OF_RANGE`/`quaternion_not_unit`, and a missing or empty frame id (default `header.frame_id`; an explicit `frame_field: null` skips the check) is `INVALID`/`missing_frame_id`. `joint_state` follows `sensor_msgs/JointState` semantics over configurable fields (defaults `name`/`position`/`velocity`/`effort`; typed `f32`/`f64` arrays and generic float lists): every array must be empty or as long as the name list (`joint_state_length_mismatch`), names must not repeat (`duplicate_joint_name`), and values must be finite (`joint_state_not_finite`) — all `INVALID`. Supporting pieces: `QualityFlags` gains `INVALID` (bit 8, product.md section 22's `invalid`; dashboards can now filter structurally-bad rows), `thadam validate` accepts both kinds (the `joint_state` array fields are checked against the dataset's declared fields, while the `pose` step's decoder-produced dotted fields, like an `enrich` table, resolve when the chain compiles at startup), and the two steps are documented in `docs/src/configuration/transforms.md` with a new concepts page.
- **`time` from a message attribute or a ROS 2 field** (`thadam-config`, `thadam-transform`): `time` takes exactly one of `field` (a JSON Pointer into the payload, now also reading a nanosecond `header.stamp`-style value with `unit: ns` as-is) or `attr` (for example `attr: mcap.publish_time` or `attr: mcap.log_time`, parsed as decimal text in `unit`), so a recorder's or publisher's clock can be the source timestamp without a payload field. Absent attributes flag `MISSING_TIME`; unparseable text is rejected like a bad payload timestamp; `max_skew` flagging is unchanged. Docs: [datasets `time`](docs/src/configuration/datasets.md#time) and [ROS 2 timestamps](docs/src/sources/ros2.md).

- **ROS 2 chain decode and the schema store** (`thadam-core`, `thadam-runtime`, `thadam-mcap`, `thadam-transform`, `thadam-config`): a durable, content-addressed schema store (`<data_dir>/schemas/<sha-256>.schema`; magic-tagged `thadam/schema-store 1` records holding name, encoding, and schema text; tmp-file/fsync/rename/dir-fsync writes, idempotent, verified on read) now lives in `thadam-core` as `SchemaStore`. The MCAP source writes every `ros2msg` channel's schema the first time the channel is seen — before the first message referencing it can be committed to the WAL — and stamps those messages with `mcap.schema_hash`; a store write failure is a classified error, never silently skipped, and the runtime hands sources the store path through the new `BuildContext::schema_dir`. Datasets gain `decode: ros2`: the chain resolves schema text from the store by hash (compiled messages cached per hash), decodes the CDR payload with `thadam-ros2-msg`, and bridges the flattened dotted fields into one payload key each, so the declared-field pipeline can read simple names today and `time: {field: /header.stamp, unit: ns}` keeps working (`/header.stamp` is one JSON Pointer token). A missing `mcap.schema_hash`, an unknown hash, and decode failures are quarantined rejects with classified codes (`decode.schema_ref_missing`, `decode.unknown_schema`, or the `decode.*`/`schema.*` codes the decoder already classifies) — never silent drops, and error text never carries payload bytes. `thadam-transform` newly depends on `thadam-ros2-msg` (permitted by `scripts/check-deps.sh`); declaring the decoder's dotted names as first-class dataset fields is the next step. Docs: [ROS 2](docs/src/sources/ros2.md), [data directory](docs/src/operations/data-directory.md).
- **Dotted dataset field names and `pose` checks at validate time** (`thadam-config`, `thadam-transform`, `thadam-arrow`, `thadam-clickhouse`): declared dataset fields may be dot-joined literal columns such as `pose.position.x` (the ROS 2 decoder's flattened spelling) — every segment follows the existing name rules, refusing leading/trailing dots and empty segments. A field may now omit `from`; the default pointer is `/<name>` as one JSON Pointer token, so a dotted name reads the decoder's flattened key. `thadam validate` resolves the `pose` step's `<prefix>.position.{x,y,z}`, `<prefix>.orientation.{x,y,z,w}` (f32/f64), and its frame field (str; `header.frame_id` by default) against the dataset's declared columns and reports each missing or mistyped one at `transforms[].prefix` / `transforms[].frame_field`, instead of deferring to chain compile at startup. The ClickHouse sink backticks identifiers in its generated SQL and compares column names verbatim from DESCRIBE through the Native block, so dotted columns map by name or through `columns`; a Parquet round-trip of dotted columns is pinned by a test.
- **`thadam export` resolves schema text from the schema store first** (`thadam-mcap`, `thadam-cli`, `thadam-runtime`): a message carrying `mcap.schema_hash` takes its schema text from `<data_dir>/schemas` by hash, so an MCAP capture made after the store existed exports with its schemas after the original files are deleted; MCAP files and `--schemas` remain the fallback for hash-less or unknown-hash messages. `SchemaResolver` gains a defaulted `resolve_hash` method (existing resolvers and closures are unchanged), two schema hashes on one topic are a conflict, and a stored schema whose name or encoding disagrees with the message is an export error naming the source and topic. Docs: [`thadam export`](docs/src/cli/export.md#schemas).
- **ROS 2 MCAP to Parquet example** (`examples/ros2-mcap-to-parquet`, ADR-0007 stage 2): a generated sample recording (`crates/thadam-mcap/examples/make_ros2_sample.rs`, git-ignored output) is decoded with `decode: ros2`, validated by the `joint_state` and `pose` steps, written to local Parquet, and exported back to MCAP. `thadam run --exit-when-sources-finish` exits once every finite source has drained, and a no-Docker CLI smoke test (`apps/thadam-cli/tests/ros2_example.rs`) runs the example end to end.
- **ROS 2 fuzz targets** (`crates/thadam-ros2-msg/fuzz`): cargo-fuzz targets `msg_parse` for the ROS 2 `.msg` parser and `cdr_decode` for the CDR decoder.
- **WAL hardware bench** (`scripts/wal-hw-bench.sh`, [runbook](docs/design/wal-hardware-runbook.md)): the script and runbook for the ADR-0004 re-run on x86 NVMe and ARM eMMC. The tooling is in; the hardware runs are not yet done.
- **CI `fuzz-smoke` job**: runs the five fuzz targets (`thadam-transform`: `chain_process`, `spec_compile`, `text_parsers`; `thadam-ros2-msg`: `msg_parse`, `cdr_decode`) for 60 seconds each on a nightly toolchain, and uploads artifacts on failure.
- **ROS 2 datasets read decoded records directly, without the JSON bridge** (`thadam-transform`): a `decode: ros2` dataset whose payload pointers are single flattened tokens — the documented spelling in declared `fields`, `time.field`, identity `{payload:...}` placeholders, `event_id` keys, and `explode` over a nested-message list — resolves each pointer to one field lookup on the decoded record and coerces the record's own values, instead of serializing every message into a flat JSON object first; the per-hash compiled-message cache now also skips the schema-store read on hits (the store is content-addressed). End-to-end through the chain on the reference Mac: `sensor_msgs/JointState` (6 joints, with the `joint_state` step) went from ~18.7 ms to ~0.44 ms per 512-message batch (~42x), and `geometry_msgs/PoseStamped` (with the `pose` step) ~100x, measured by the new `cargo bench -p thadam-transform --bench ros2_decode`. The bridge remains only for the pointers a record cannot serve (nested or indexed multi-token pointers such as `/name/0`, and `explode` over a typed array), materialized per message that needs one. One lossy behavior of the bridge is fixed by this: non-finite floats used to become `null` — a `pose` step read them as `pose_missing_field`, a NaN typed array was rejected at extraction, and a `required` float field rejected the message; they now reach the `pose`/`joint_state` steps as non-finite values and are flagged `pose_not_finite`/`joint_state_not_finite` as designed, `Bytes` stay bytes, and a `Ts` stays a timestamp end to end. Docs: [ROS 2](docs/src/sources/ros2.md).
- **`thadam-opcua`**: OPC UA subscription source (`kind: opcua`, owner decision: `async-opcua` `=0.19.0` pinned, client only, MPL-2.0 with `deny.toml` exceptions scoped to its tree, never `open62541`), registered in `thadam-cli` behind the default-off `opcua` feature and added to the `scripts/check-deps.sh` direction rules. One subscription per source over the configured `nodes`; each publish response becomes one JSON message grouping that response's data changes (`{ "<name>": value, ..., "ts_us": <newest source timestamp, else newest server timestamp, else receive time> }`) with attributes `opcua.endpoint`, `opcua.subscription_id`, and `topic = opcua/<endpoint host>/<subscription>`. Config: `endpoint` (opc.tcp URL with explicit port), explicit `security_policy` (`none`/`basic256sha256`/`aes128_sha256_rsaoaep`/`aes256_sha256_rsapss`, no default, like `on_full`) + `security_mode` validated against it, `auth` anonymous or username (password via `${file:}`/`${env:}`, redacted; certificate auth is step 2), client-cert material required for secured policies, per-item `sampling_interval`/`queue_size`, `publishing_interval`, and `reconnect` (`min_backoff`/`max_backoff`/`max_handshakes_per_minute`). Values map to the documented JSON subset (Bool/integers/Float/Double/String/DateTime→RFC 3339/ByteString→base64/numeric-boolean arrays); a non-Good status becomes `null` named `name=StatusCode` in `opcua.bad_status`, an unsupported variant type becomes `null` named in `opcua.unsupported`, and client-side drops ride on later messages as `opcua.dropped` — nothing silently lost. Delivery is at-most-once per publish response (`ack_mode: none`, documented why). Connection loss is transient and transparent: a supervisor reconnects with jittered backoff, re-creating the subscription, every attempt rate-limited by a GCRA handshakes-per-minute limiter (the `rsa` 0.9 RUSTSEC-2023-0071 timing-sample bound, with a time-boxed `deny.toml` advisory exception reviewed by 2027-04-01 and the AES policies preferred). Rejected credentials and channel certificates are **fatal** (`auth.failed`), not retried. Tests run an `async-opcua` server in-process (`server` feature as dev-dependency only): subscribe and value mapping with grouped payloads and attributes, a Bad status becoming `null` + attribute, server restart with reconnect and resubscribe, handshake-rate-limit counting under paused tokio time (unit), exhaustive config validation, `basic256sha256`/`sign_and_encrypt` with generated self-signed certs (verified in-process this step), and wrong-password fatality. Docs: [OPC UA](docs/src/sources/opcua.md).
- **`thadam-opcua` step 2**: X.509 user authentication (`auth: {kind: certificate, cert, key}`, validated at config time: files parse and the key matches the certificate; requires a secured policy); server certificates are refused by default, with pinning through `cert.trust_server_certs` and an insecure opt-in `cert.accept_unknown_server_cert`; `mode: poll` with `interval` (one Read per poll over all nodes, one message per poll, same JSON shape and Bad-status handling, server-restart recovery); end-to-end tests for `aes256_sha256_rsapss` and `aes128_sha256_rsaoaep` (`sign_and_encrypt`, and `sign` for aes128) against an in-process server, plus fatal, non-retried certificate rejections.
- **`thadam-ros2-live`**: the live ROS 2 source (`kind: ros2_live`, ADR-0007 stage 4, **experimental**), registered in `thadam-cli` behind the default-off `ros2-live` feature. It subscribes through a `rmw_zenohd` router over a raw Zenoh 1.10.1 client (the spike S3 mapping: client mode, multicast scouting off, `<domain>/<topic>/**` key expressions, 33-byte attachments) behind the Thadam-owned `LiveRos2Transport` trait; `rmw_zenoh` is the only transport in this step — a zenoh-bridge-ros2dds sidecar comes later, only if needed, and liveliness discovery is out of scope (topics are an explicit `{ name, type }` list, with optional per-topic `transient_local` running the spike's four-stricture late-join query for `/tf_static`). Schemas are assembled from `msg_dirs` (required: there is no recording to read them from) into the MCAP-style `ros2msg` text, compile-checked at build, and written to the schema store before the first message referencing them can be committed; messages carry `mcap.schema_hash` plus `topic`, `ros2.type`, `ros2.type_hash` (RIHS01 is informational — keyed by type name, `thadam-ros2-msg` does not compute REP-2016 hashes), `ros2.seq`, `ros2.gid`, `ros2.source_time`, and `ros2.late_join` attributes, so existing `decode: ros2` datasets and `thadam export` work unchanged. Delivery is at-most-once (`ack_mode: none`): sequence gaps per publisher GID and client-side queue overflow are counted in a running `ros2.dropped` attribute (never silently lost, never blocking the Zenoh callback), and a lost session reconnects with jittered backoff. Dependency policy: `serde_yaml` is exceptioned solely as a mandatory dependency of `zenoh-config` 1.10.1, and `option-ext` (MPL-2.0) has a one-crate license exception; `aws-lc-sys`/`openssl-sys` stay out with the feature on. Tests: unit coverage (config, attachment parsing, key expressions, gap counting, schema assembly, overflow counting) plus an ignored Docker end-to-end test (public `ros:jazzy-ros-base` image + `ros-jazzy-rmw-zenoh-cpp`, `cargo nextest run -p thadam-cli --features ros2-live --run-ignored only -E 'binary(ros2_live_docker)'`) that captures ~10 s through a real pipeline with `decode: ros2` datasets to Parquet and asserts rows per topic, zero decode errors, and the `/tf_static` late join. Docs: [ROS 2 live](docs/src/sources/ros2-live.md).
- **`thadam-iceberg`**: the Apache Iceberg registrar (`kind: iceberg`, P2, **experimental**, phase-4 step 1; [design note](docs/design/iceberg-append.md)), registered in `thadam-cli` behind the default-off `iceberg` feature (`iceberg`/`iceberg-catalog-rest` `=0.10.1`, Apache-2.0, no `aws-lc-sys`/`openssl-sys`: the opendal storage path was rejected for pulling `aws-lc-sys`, so the crate's `iceberg::io::Storage`/`StorageFactory` run over the workspace's audited `object_store` S3 stack; the `iceberg` crate builds arrow/parquet 58 alongside the workspace's 60 and reqwest 0.12 alongside 0.13, and MSRV for this one crate is Rust 1.94). A `sinks:`-entry service like `object_store`, it consumes the same segment catalog (`from`) and registers every uploaded segment into one unpartitioned format-v2 table per dataset (`{namespace}.{dataset}`) via `fast_append` — no Parquet rewrite, since ADR-0013 field IDs are already on disk. Config: `from`, `pipeline` (must match the shipper's), `catalog_uri`, `url` (`s3://bucket/prefix`), `namespace` (dotted levels), `create_table` (off by default), `store` (endpoint/region/allow_http/creds), `retry`. Created tables keep the file's own field IDs: the initial metadata JSON is authored client-side and adopted with `register_table`, because Iceberg reassigns IDs at REST `create_table` (verified against `apache/iceberg-rest-fixture:1.10.1`). Existing tables are validated once per dataset per run from a segment footer (present-by-ID, promotable types; mismatch is fatal `sink.iceberg_schema_mismatch`). Datasets therefore registered need the `unsigned: signed` Arrow policy — Iceberg has no unsigned types and the default `Native` envelope has `UInt64` lineage columns (fatal `sink.iceberg_unsupported_type`, naming the fix). No duplicate data files across crashes, restarts, and commit conflicts: committed segment keys ride in snapshot summaries, rebuilt on load and after failures, and conflicts reload the table before retrying. Catalog unreachability and S3 IO failures retry forever (visible); auth, schema, and config errors are fatal. Supporting piece: `thadam-segments` keeps the uploaded object key in memory and exposes `catalog.uploaded()` for the registrar. Step 1 limits: no schema evolution (step 2), unpartitioned, no column metrics on data files, one bucket for metadata and data. Docker-gated tests (`cargo nextest run -p thadam-iceberg --run-ignored only -E 'binary(docker_iceberg)'`, public images `chrislusf/seaweedfs:3.81` with S3 auth enabled and `apache/iceberg-rest-fixture:1.10.1` with `AWS_REQUEST_CHECKSUM_CALCULATION=when_required` — SeaweedFS 3.81 rejects classic aws-chunked with auth off and cannot unwrap SDK v2 trailing-checksum writes): a real segment pipeline to SeaweedFS, table scan with row counts, field IDs (`{1..11, 1000}`), and read-back values, a registrar restart proving no second data file, and a pre-created mismatched table failing fatally. Docs: [Apache Iceberg](website/docs/src/sinks/iceberg.md).
- **Iceberg step 2: schema evolution, conflict test, HTTPS catalog** (`thadam-iceberg`, experimental; [design note](docs/design/iceberg-append.md)): before each segment is appended, its footer schema is merged into the table by Parquet field ID — new IDs are added as optional columns with their own IDs, a known ID under a new name is renamed, `int`→`long`, `float`→`double`, and wider decimal precision are promoted, and dropped columns stay; narrowing, an ID reused with another type, any required-ness change, a missing required column, and a new ID reusing a column name are fatal `sink.iceberg_schema_mismatch` listing every reason, with the table untouched. `iceberg` 0.10.1 cannot do this itself (`update_schema` renumbers added columns and has no rename or promotion, and `TableCommit` cannot be built outside the crate), so the schema commit (`add-schema` + `set-current-schema` with `assert-table-uuid`/`assert-current-schema-id`/`assert-last-assigned-field-id`) is POSTed to the REST update endpoint; schema and append are two commits, schema first, and a crash between them is safe because the merge is idempotent (re-derived as "no change") and the evolved schema only adds nullable columns or lossless widenings. New config key `catalog_ca_file` (PEM, `https://` catalogs only) replaces the platform trust roots for the catalog connection via `RestCatalogBuilder::with_client`; an untrusted certificate is a fatal `config.invalid` that names the TLS cause instead of an endless retry. The in-process conflict tests (a `MemoryCatalog` wrapper commits a competing writer just before the registrar's commit) assert a stale or conflicting writer neither loses nor duplicates a data file. New Docker tests (public images, pinned): schema evolution end to end (int→long + new column + rename, values read back, narrowing fatal and table unchanged) and `caddy:2.10.2` terminating TLS with an `rcgen` test CA in front of `apache/iceberg-rest-fixture:1.10.1` (works with the CA including the schema commit, fails fast and fatally with another CA and with none). Limits: the schema commit sends no authentication header (the registrar has no catalog credentials yet), no mutual TLS to the catalog, and every unregistered segment's footer is read once. Docs: Apache Iceberg (`website/website/docs/src/sinks/iceberg.md`).

### Fixed

- **`thadam-cli` crypto provider**: the composition root now installs the ring rustls crypto provider at process start. `object_store`/`reqwest` are built `rustls-no-provider` (ADR-0020), so every `thadam run` of a config with an `object_store` sink previously panicked with "No rustls crypto provider is configured" when the shipper built its S3 client (PR15 end-to-end discovery); the MQTT TLS relay builds on the same provider.
- **`thadam-object-store` probe**: the startup capability probe checked user-metadata round-trip *after* the conditional-create conflict put. On stores that ignore `If-None-Match` (observed on SeaweedFS 3.81) that second create overwrites the probe object and its attributes, so the probe reported `returns_metadata = false` for stores that do return metadata, silently degrading conflict verification to size-only. The metadata check now runs before the conflict put.
- **`thadam-config`**: the config now accepts all eight transform kinds the engine implements — `sample`, `enrich`, `rename`, `project`, and `cast` are added to `validate`, `on_change`, and `filter`, using the engine's option names.
- **`thadam-config`**: the config gains the engine's `null:` predicate test, the `on_change` `{ field, deadband }` entry form, and `unit: rfc3339` with `default_offset` for dataset `time`.
- **`thadam-config`**: `dedup` without `event_id.key` is now a validation error (`config.invalid`); it was a warning. This matches ADR-0011 D17.
- **`thadam run`**: the logging guard now stays alive for the whole run; application log lines after startup are no longer silently dropped.
- **Log-format spellings** are unified on `json`/`pretty`: config `observability.logs.format` takes those values with `text` accepted as a deprecated alias for `pretty` (validation warns), and `thadam run` without `--log-format` uses the config value (default `json`) instead of the previously hardcoded `pretty`.
- **`thadam-runtime` quarantine no longer holds its sink's cursor**: a reject used to cap the owning segment sink's WAL cursor (`Quarantine::floor`) until the quarantine Parquet segment rotated and became durable (`quarantine.rotation.max_age`, 5 minutes by default), pausing the sink's cursor, its uploads, and shipping behind one pending reject. Rejects are now appended and fsynced to a small per-quarantine staging file (`quarantine/<sink>/rejects.staging`: append-only frames of `len | crc32c | payload`, one per push) and the cursor may pass them as soon as that fsync returns; the quarantine segment is built from the same rows on its own rotation cadence and staging is truncated (or rewritten without its dead prefix) once the covering segment is durable. After a crash, staged rejects not yet in a durable quarantine segment are replayed into the next one exactly once, filtered by the quarantine's durable WAL position, with torn staging tails cut like the WAL's. Staging bytes are charged to the quarantine disk budget, the open quarantine segment is closed early when about 8 MiB is staged or the budget is full, and a failed quarantine append is healed by replaying staging. Quarantine segment ranges now chain contiguously across pushes: before, two rejects separated by a quarantine rotation left a hole that stalled the quarantine watermark. No configuration change. New failpoint `quarantine::after_stage`.
- **`thadam-runtime` / `thadam-segments` sink-level rejects survive a crash after the sink's segment is durable**: a reject the sink itself returns from `append` (for example a value its columns cannot hold) is only known after `append`, but the Parquet sink could finalize the segment holding that batch inside the same `append` (rotation by rows or bytes, or eviction at `max_open_files`). A crash before the reject was staged left a sink position the restart treated as complete, the re-read skipped the sink append, and the reject was never regenerated. `SegmentSink` gains a defaulted `defer_durability(bool)`; the segment driver sets it, and the Parquet sink then runs a rotation or eviction that the current batch triggers at the start of the next `append`, `poll_commit`, or `finalize_all`, always after the driver staged the batch's rejects. New failpoint `segment::after_append_before_stage`.
- **`thadam-kafka` TLS and SASL rejections are fatal at connect**: rskafka 0.6.0 retried every connect failure until its deadline and then reported only text, so an untrusted broker certificate, a client certificate the broker refused, and a rejected SASL login were retried as transient errors. The sink now recognises those messages and fails fatally (`config.invalid` for the certificate, `auth.failed` for the client certificate and SASL). A connect is bounded at three `request_timeout`s instead of one, so the cause is reported before the bound fires (this supersedes the one-`request_timeout` connect bound stated in the bullet above). A topic deleted mid-run now reports that it is missing or was deleted. Docker tests run TLS, mutual TLS, SASL PLAIN and SCRAM over TLS, and an authorizer denial against `apache/kafka` 4.3.1; [the Kafka page](docs/src/sinks/kafka.md#tested-combinations) lists exactly what ran.
- **`thadam run` reads `observability.admin`**: the admin API (`/healthz`, `/readyz`, `/metrics`, `/status`) now starts from the configuration — `bind` (defaulting to loopback `127.0.0.1:9464` when the section is absent) and `token_file` — with `thadam run --admin-bind` and `--admin-token-file` overriding it for a single run. Previously the section was validated but ignored, so the API served only when `--admin-bind` was passed. The rule that a non-loopback bind requires a token (config validation plus the server's own check) is unchanged.
- **`thadam run` logs are no longer lost when stderr is a pipe** (for example under `docker logs`): the CLI held the process-wide stderr lock for the whole run, so the non-blocking logging worker could not write a single line until the lock was released at exit — and only a fragment drained before the process died. The lock is now taken per write, so lines appear while the pipeline runs and the shutdown lines are flushed on a graceful stop.
